## Day 2：整体与局部

上一轮任务中的第 2 项是“画整体数据流”，第 3 项是“解释每个模块的输入、
输出和作用”。两项不是新算法，而是从两个层次阅读同一份代码：

- 整体：数据从哪里来，依次经过哪些模块，最后输出什么？
- 局部：进入一个模块后发生什么变换，为什么需要它，输出如何交给下一模块？

阅读入口是 [qwen3.py](../reasoning_from_scratch/qwen3.py)，顺序如下：

```text
QWEN_CONFIG_06_B
→ Qwen3Model.forward
→ TransformerBlock.forward
→ GroupedQueryAttention.forward
→ FeedForward.forward
```

### 第 2 项：理解整体数据流

先追踪 `Qwen3Model.forward` 中的变量 `x`。每看一行就问：
“当前的 x 表示什么，形状是什么，这行代码改变了什么？”

设 `B=1`、`T=8`：一次处理 1 条输入，每条有 8 个 token。
这里是举例，不表示 8 个字或 8 个单词一定会编码为 8 个 token。

```text
token IDs                          [1, 8]
    |
    | tok_emb：根据 token 编号查表
    v
初始 token 向量                     [1, 8, 1024]
    |
    | 28 个 Transformer Block：逐层更新表示
    v
包含上下文信息的向量                  [1, 8, 1024]
    |
    | final_norm：归一化
    v
归一化后的向量                       [1, 8, 1024]
    |
    | out_head：投影到词表
    v
logits                             [1, 8, 151936]
```

关键代码对应：

```python
tok_embeds = self.tok_emb(in_idx)
x = tok_embeds
# 省略 Mask、位置和 Cache 管理
for i, block in enumerate(self.trf_blocks):
    x, new_blk_cache = block(...)
x = self.final_norm(x)
logits = self.out_head(x.to(self.cfg["dtype"]))
return logits
```

这是定位代码流程的摘录，`block(...)` 省略了实际参数，不是可直接执行的示例。

| 数值 | 含义 |
| --- | --- |
| `1` | Batch 中有 1 条输入 |
| `8` | 本次输入有 8 个位置 |
| `1024` | 每个位置的隐藏向量维度 |
| `28` | Transformer Block 的层数 |
| `151936` | 词表候选 token 的数量 |

`[1, 8, 1024]` 表示每个位置用 1024 个数描述；
`[1, 8, 151936]` 表示每个位置为词表中的候选 token 输出分数。
不要把向量的每个维度直接解释成某个固定的人类概念。

**28 层是处理深度，不是一次生成 28 个 token。** 每个 Block 更新表示，
不负责向输入序列追加位置，因此一次前向中的 8 个位置经过 28 层仍是 8 个位置。

### logits 如何变成文字

`forward` 返回的是未归一化分数，不是概率，也不是一句话。
在这个因果语言模型中，每个位置的输出用于预测该位置之后的下一个 token。
继续生成时先取最后一个位置：

```python
logits = model(input_ids)                  # [B, T, vocab_size]
last_scores = logits[:, -1, :]             # [B, vocab_size]
next_id = last_scores.argmax(dim=-1)       # [B]，贪心选择
```

这是说明形状的片段，需要已经初始化的模型和输入。实际的 Cache 生成循环见
[ch02.py](../reasoning_from_scratch/ch02.py) 中的
`generate_text_basic_stream_cache`：

1. 模型处理输入，得到最后位置的 logits。
2. 当前代码用 `argmax` 选择得分最大的 token 编号。
3. tokenizer 将编号解码为文本片段。
4. 如果还需要继续生成且没有结束，将新 token 送入模型，复用 KV Cache。

当前贪心生成不需要先计算 softmax；其他采样方式再另行学习。
一个 token 不一定是一个完整单词，所以模型是逐 token 生成，不是每次生成一句话。
脚本中的编码、生成和解码入口见
[generate_simple.py](../ch02/05_use_model/generate_simple.py)。

### 第 3 项：理解模块职责

先别背模块名称，盯住一句话里的一个位置：

```text
[我] [拿起] [一个] [杯子] [它] [装着] [热] [水]
                        ↑
                    只观察这一行
```

这是人为划分的位置，不是 tokenizer 实测。实际进入 Block 时，“它”不是一个
字符串，而是一行 1024 个数。第一次进入时来自 Embedding；进入后续 Block 时，
已经包含前面各层的计算结果。所有位置都在计算，这里只追踪其中一行。

#### 先看完整的一次更新

把一个 Block 看成两次“保留原稿，再加上计算分支产生的更新”：

```text
这一行的当前向量 x0
    |---------------------------------|
    |                                 |
    v                                 |
 norm1：调整数值尺度                    | 原样保留 x0
    |                                 |
    v                                 |
 Attention：汇集允许访问的上下文         |
    |                                 |
    v                                 v
  更新量 a --------------------------> 相加
                                       |
                                       v
                                   x1 = x0 + a
                                       |
    |----------------------------------|
    |                                  |
    v                                  |
 norm2：再次调整数值尺度                 | 原样保留 x1
    |                                  |
    v                                  |
 FFN：对每个位置内部的特征做非线性变换    |
    |                                  |
    v                                  v
  更新量 f --------------------------> 相加
                                       |
                                       v
                                   x2 = x1 + f
```

图中的“更新量”是计算结果用于残差相加时的角色，不代表改动一定很小，
也不保证每层计算都能对应某条人类可读的推理结论。
两个保留分支绕过归一化和变换：加回的是 `x0` / `x1`，不是归一化后的向量。

#### Embedding：把编号换成可计算的一行数

可以把它想成按编号领取一张初始记录表：

```text
token ID → 查 Embedding 权重表 → 一行 1024 个数
```

这不是查询字典里的中文释义。相同 token ID 从同一张表取出的初始向量相同；
后续经过 Attention 等计算，处在不同上下文中的表示才可能不同。
Embedding 在 28 个 Block 之前执行，不是每个 Block 都重新查一次表。

#### RMSNorm：调整这一行的整体尺度，不替它查上下文

把一行数想成一组信号，RMSNorm 先按这一组信号的整体强度调整尺度，
再逐特征乘上学到的缩放参数。缩小到只有两个数、忽略 epsilon，
并假设缩放参数都为 1：

```text
输入 x = [3, 4]
RMS = sqrt((3² + 4²) / 2) ≈ 3.536
输出 x / RMS ≈ [0.849, 1.131]
```

仍然是两个数，只是尺度变了；没有读取其他 token，也没有变成候选文字。
它不是把数都裁剪到 `[0,1]`，也不是减去均值。实际模型对每个位置的
1024 个特征做这件事，并使用可学习的逐特征缩放。

#### Attention：允许这一行去取前面几行的信息

在“它”这个位置，允许读取的范围是：

```text
[我] [拿起] [一个] [杯子] [它] | [装着] [热] [水]
 <--------- 允许 -----------> | <--- 不允许 --->
                              因果 Mask 边界
```

先把一个 head 的加权汇集简化成“只有三行、每行两个数”的例子：

```text
行A的 Value = [2, 0]   权重 0.1
行B的 Value = [0, 4]   权重 0.8
行C的 Value = [1, 1]   权重 0.1

汇集结果 = 0.1×[2,0] + 0.8×[0,4] + 0.1×[1,1]
         = [0.3, 3.3]
```

权重和 Value 都是人为给定的形状示例，不是“它”位置的实测输出。
真实实现先生成 Q/K/V，以 Q/K 和位置相关计算得到权重，再汇集 V；
多 head 的结果拼合、投影成 1024 维后，作为图中的 `a`。
Q/K/V 的详细形状在 Day 3 验证。

“它”可能因此获得与前面“杯子”相关的信息，但不能保证某个 head 只关注“杯子”，
也不能把任何一维直接命名为“杯子”。本节要看懂的是信息可以跨位置流动。

#### FFN：不再读取其他行，展开加工这一行已有的特征

到 FFN 时，“它”这一行已经经过 Attention 和第一次残差相加。
FFN 对这行数做变换，不再直接读取“杯子”那一行：

```text
输入这一行 x1
    |
  norm2
    |
    |-- fc1 → 3072个数 → SiLU --|
    |-- fc2 → 3072个数 ---------|→ 逐元素相乘 → fc3 → 1024个数
```

两条分支是同一个输入经不同权重计算得到的，不是复制粘贴同一份数字。
SiLU 分支参与调节另一分支的特征，形成门控；不是逐 token 做硬性的
“通过/不通过”判断。最终投影成图中的 `f`，再与 `x1` 相加。

所有位置使用同一个 FFN 的参数，但分别处理各自的输入；“逐位置计算”
不表示没有上下文，因为上下文已经进入它的输入向量。

还不清楚 `gate_proj / up_proj / down_proj` 和 SiLU 时，继续阅读
[RoPE 与 SwiGLU 的形象解释](ROPE_SWIGLU_INTUITION.md)，并在
[配套 Notebook](../learning/day03_rope_swiglu.ipynb) 中观察旋转、曲线和数值。

#### 残差：保留当前状态，加上分支结果，不是换成分支结果

用只有两维的示意数字走完两次相加：

```text
Block 输入 x0 = [1.0, 2.0]
Attention 分支得到 a = [0.3, -0.2]
第一次相加 x1 = x0 + a = [1.3, 1.8]

FFN 分支得到 f = [0.1, 0.4]
第二次相加 x2 = x1 + f = [1.4, 2.2]
```

这些分支结果是为了演示相加而假设的，不是由前面的 Value 例子推导出来的。
真实向量是 1024 维，但相加规则一样。第二次保留的是已经更新过的 `x1`，
不是重新拿最初的 `x0`。因此可以把整个 Block 记成：

**保留当前状态 → 联系上下文 → 合并更新 → 加工特征 → 再合并更新。**

#### 输出投影：最后才从内部特征转为候选分数

经过 28 个 Block 后，每个位置仍是一行 1024 个特征。
模型再做 `final_norm`，随后 `out_head` 给这一行对应的词表候选项打分：

```text
内部特征 [B,T,1024] → out_head → 候选分数 [B,T,151936]
```

`final_norm` 和 `out_head` 在 28 个 Block 之后，不属于每个 Block 的内部步骤。
文字解码更在模型 forward 之外，不要把这些步骤都叫作 Attention。

#### 将动作对应回源码

| 看图时的动作 | 仓库里的代码 | 主要形状 |
| --- | --- | --- |
| 初始编号变向量 | `self.tok_emb(in_idx)` | `[B,T] → [B,T,1024]` |
| 保留输入 | 第一次 `shortcut = x` | `[B,T,1024]` |
| 调整输入尺度 | `self.norm1(x)` | 不变 |
| 联系上下文 | `self.att(...)` | 主输出回到 `[B,T,1024]`，另返回 Cache |
| 第一次合并 | 第一次 `x = x + shortcut` | 不变 |
| 保留更新后的状态 | 第二次 `shortcut = x` | `[B,T,1024]` |
| 调整当前尺度 | `self.norm2(x)` | 不变 |
| 加工每个位置的特征 | `self.ff(x)` | `1024 → 3072 → 1024` |
| 第二次合并 | 第二次 `x = x + shortcut` | 不变 |
| 28 层后的归一化和打分 | `self.final_norm`、`self.out_head` | `[B,T,1024] → [B,T,151936]` |

28 个 Block 的结构相同，但参数各自独立。上面的整张流程图执行一次才是一个
Block，不是每一个小动作各算一层。

要把流程图变成可验证的证据，接着阅读
[Day 3 调试实验](DAY03_SHAPES_DEBUGGING.md)：它会实际捕获模块输出、
检查两次残差相加，并演示怎样在原始代码中打断点。

## Day 2 验收问题

先不看参考答案，自己用完整句子回答：

1. 为什么经过 28 个 Block，序列长度仍然是 8？
2. Attention 和 FFN 的作用有什么区别？
3. 为什么 `model(input_ids)` 返回 logits，而不是直接返回文字？
4. `[1,8,1024]` 和 `[1,8,151936]` 的最后一维各代表什么？

## 五个问题的形象解释

统一使用一个画面：输入的 8 个 token 对应一张表的 8 行，每行有 1024 个数。
“记录表”只是帮助理解形状，实际是浮点张量；每个数不对应固定的人类概念。

### 1. 经过 28 个 Block，为什么还是 8 个位置？

想象 8 张记录表依次经过 28 道加工步骤。每道步骤改写表里的内容，却不新增或
删除记录表：

```text
8 行 × 1024 列
    ↓ Block 1：更新数值
8 行 × 1024 列
    ↓ Block 2：再次更新数值
    ...
    ↓ Block 28
8 行 × 1024 列
```

这里有两个不同的“次数”：

- 模型深度：同一批位置经过多少层计算，这里是 28 层。
- 生成长度：外部循环向序列增加了多少个新 token。

例如，输入有 8 个 token，28 层算完后，用最后位置的分数选择第 9 个 token。
将新 token 追加到完整序列，是生成循环做的，不是某个 Block 做的。
有 KV Cache 时，下一次前向通常只输入这 1 个新 token，先前 8 个位置的 K/V
从 Cache 读取，所以也不要把“完整序列长度”和“本次 forward 输入长度”混为一谈。

**一句话：28 层改变每行的内容，生成循环才增加新的一行。**

### 2. Attention 和 FFN 分别在做什么？

把 8 个位置仍看作 8 行：

```text
Attention：不同的行之间取信息，再更新当前行
FFN：拿到更新后的每一行，对这一行内部的数做变换
```

用一句人为划分的例子：

```text
[我] [拿起] [一个] [杯子] [它] [装着] [热] [水]
 1     2      3      4     5      6     7    8
```

这只是便于讲解的 8 个位置，不是实际 tokenizer 的编码结果。

在第 5 个位置“它”：

- Attention 可以从前面的“杯子”等位置汇集信息，更新“它”的表示。
- FFN 接收已经包含这些上下文的向量，对其进行非线性特征变换；这一步本身
  不再去读取“杯子”那一行。
- 因果 Mask 不允许第 5 个位置读取后面的“装着、热、水”。

这不是说某个 head 必定只关注“杯子”，也不是说某个特征维度就叫“杯子”；
只是解释允许的信息流向，实际权重和表示需要观察模型才知道。

可以把 Attention 记为“联系上下文”，FFN 记为“加工当前表示”。FFN 在各位置
使用同一套参数，但输入数值不同，输出通常也不同。

**一句话：Attention 在位置之间汇集信息，FFN 在每个位置内部加工特征。**

### 3. 为什么返回 logits，不直接返回文字？

想象模型为“接下来接什么”交出一张打分表：

| 候选 token | 示意分数 |
| --- | --- |
| 水 | 5.2 |
| 茶 | 4.8 |
| 车 | -1.0 |

分数和文字只是示意，不是本次模型的实测输出。真实的表是以 token ID 为索引的
151936 个分数，不是直接保存中文字符串。logits 可以大于 1 或小于 0，它们不是概率。

随后还需要两个动作：

```text
模型 forward：给候选项打分
    ↓
生成策略：选择一个 token ID
    ↓
tokenizer：把 ID 解码为文字片段
```

当前的贪心策略会选择最高分的“水”对应的 ID；如果改用其他采样策略，选择可以
不同，而模型的 forward 不必重写。这就是把“打分”“选择”和“解码”分开的意义。

**一句话：模型交出候选分数，生成策略做选择，tokenizer 才把编号变成文字。**

### 4. 1024 和 151936 有什么区别？

同样是 8 行，表格的“列”换了含义：

```text
[1,8,1024]：
第 1 行：特征数1  特征数2  ... 特征数1024
...
第 8 行：特征数1  特征数2  ... 特征数1024

[1,8,151936]：
第 1 行：ID0分数  ID1分数  ... ID151935分数
...
第 8 行：ID0分数  ID1分数  ... ID151935分数
```

- `1024`：用于内部计算的一行特征向量。1024 个数需要结合起来理解，
  不能直接查词表把某个维度读成文字。
- `151936`：词表中每个候选项各有一个分数，列索引具有明确的 token ID 含义。
- 前面的 `1` 和 `8` 没变，仍然是一条输入、8 个位置。

`out_head` 就是将“一行 1024 个内部特征”映射成“一行 151936 个候选分数”。
继续生成时取第 8 行的分数预测第 9 个 token，不是在重新判断第 8 个 token 是什么。

**一句话：1024 列描述当前位置，151936 列给下一个 token 的候选项打分。**

### 5. 为什么 FFN 扩到 3072，又回到 1024？

可以把 FFN 看成“统一格式的输入表，中间允许使用更宽的计算区”：

```text
输入：1024 列
    ↓ 两个学习到的线性投影
中间：各 3072 列，经过 SiLU 和门控相乘
    ↓ 学习到的输出投影
输出：1024 列
    ↓ 与保留的原输入逐元素相加
下一层：1024 列
```

更宽的中间层提供更大的非线性特征变换空间；不是复制三份原始向量，
也不表示可以把 3072 个数无损压缩回 1024 个数。

为什么一定要回到原来的维度？看一个缩小版的形状演示：

```text
保留的原输入：       [1.0, 2.0]           2 个数
分支内部的宽向量：   [3.0, 4.0, 5.0, 6.0] 4 个数
```

2 个数和 4 个数不能直接逐元素相加。先把宽向量投影回 2 个数，例如：

```text
分支投影结果：       [0.3, 0.7]
残差相加：           [1.0, 2.0] + [0.3, 0.7] = [1.3, 2.7]
```

数字只演示形状，不是实际 FFN 的权重计算结果。真实模型把“2 → 4 → 2”换成
“1024 → 3072 → 1024”，确保残差加法和后续 Block 的接口一致。
`3072` 是这个模型的中间层配置，并不是所有模型都必须使用这个数字。

**一句话：中间可以展开加工，交回残差主路径时必须恢复相同形状。**
