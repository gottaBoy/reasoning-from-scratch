# RoPE 与 SwiGLU：把位置旋转和特征门控分开理解

配套 [Day 3 交互实验](../learning/day03_rope_swiglu.ipynb) 可以直接在 Jupyter
运行，观察旋转图、SiLU 曲线和仓库代码的数值结果。不下载权重，不修改模型源码。

## 1. 先分清它们在哪里

```text
Attention 内部：
x → Q/K/V 投影 → Q/K 归一化 → Q/K 应用 RoPE → 打分、Mask、softmax → 汇集 V

FFN 内部：
x → gate_proj → SiLU --|
                      |→ 逐元素相乘 → down_proj → 输出
x → up_proj ----------|
```

它们不是同一个模块的前后几步：

- RoPE 帮助 Attention 的比较包含位置信息。
- gate/up/down + SiLU 构成这里的 SwiGLU FFN，对每个位置的特征做非线性变换。

## 2. RoPE：像给 Q/K 的二维分量装上旋转指针

先只看一对数，把 `[1,0]` 画成平面上朝右的箭头：

```text
       y
       ^
       |
       O------> x
         [1,0]
```

假设每往后一个位置，箭头转 30 度：

| 位置 | 旋转角度 | `[1,0]` 旋转后的示意值 |
| --- | --- | --- |
| 0 | 0 度 | `[1.000,0.000]` |
| 1 | 30 度 | `[0.866,0.500]` |
| 2 | 60 度 | `[0.500,0.866]` |

这里的 30 度只是画图示例，不是 Qwen3 的真实位置增量。
“转”是同时改变这一对特征数，不是把 token 在句子里移动，也不是新加两个维度。

真实 RoPE 的二维旋转为：

```text
新的第1个数 = a*cos(angle) - b*sin(angle)
新的第2个数 = a*sin(angle) + b*cos(angle)
```

### 为什么旋转后可以比较相对位置

Attention 会比较 Q 和 K。固定它们旋转前的内容时，可以理解成比较两根指针：

```text
Q 在位置2：转60度
K 在位置5：转150度
相差90度

整体平移3个位置：
Q 在位置5：转150度
K 在位置8：转240度
仍相差90度
```

点积会受到相对角度的影响。数学上，旋转后的点积可以写成包含位置差的形式：

```text
(R(m)q) · (R(n)k) = q · R(n-m)k
```

所以它不是把“位置编号”直接塞进某一列，而是通过旋转让 Q/K 的相似度带上
相对位置因素。上面的等式固定了旋转前的 q/k；真实模型的 q/k 内容也会变化，
不能推断“相同距离的两个词一定具有相同 Attention 分数”。

### 128 维时，不是只有一根指针

把一个 128 维 head 分成 64 对特征，每一对都像一根二维指针，并采用不同的
旋转频率：有的转得快，有的转得慢。这些不同的相位一起表达位置关系。
不要把它简化成“离得越远分数必定越低”；单个频率会周期性旋转。

当前仓库采用 split-halves 配对。4 维时是：

```text
[a,b,c,d] → (a,c) 一对，(b,d) 一对
```

不是在这个实现里按 `(a,b)`、`(c,d)` 配对。128 维时对应 `0↔64`、
`1↔65` 等，具体代码见
[compute_rope_params / apply_rope](../reasoning_from_scratch/qwen3.py)。

当前 Attention 对 Q/K 应用 RoPE，不对 V 应用。RoPE 保持张量形状不变，
因果 Mask 才负责禁止看未来。Cache 推理时不能把新 token 的位置重新当成 0，
位置 offset 将在 Day 4 继续验证。

**记忆句：内容生成 Q/K，位置决定怎样旋转，旋转后的点积同时考虑内容和位置。**

### “转 360 度不是又回来了吗？”

是的，**只看一对特征时，确实会回来**。这不是理解错了，而是 RoPE 的周期性。
关键在于：RoPE 不是只有一只时钟，而是同时使用很多只转速不同的时钟。

用两个人为的周期来想：

```text
时钟 A：每 4 个位置转一圈
时钟 B：每 7 个位置转一圈
```

位置 `1` 和 `5`：

```text
时钟 A：5 - 1 = 4，已经转满一圈，看起来相同
时钟 B：5 - 1 = 4，还没有转满 7，状态不同
```

因此两只时钟合在一起，仍能区分位置 `1` 和 `5`。
只有两个周期同时重合时才真正撞车；这个例子要到 28 个位置后才同时重复。

真实 RoPE 不是简单的 4/7 周期，而是每一对特征使用不同频率：

```text
第 1 对：转得快，周期短
第 2 对：稍慢
第 3 对：更慢
...
最后一对：转得很慢，周期很长
```

Qwen3 的 head_dim 是 128，因此每个 head 有 64 对旋转特征。
在 `rope_base=1_000_000` 的配置下，最快的一对会快速循环，最慢的一对的周期
远大于 40960 的训练上下文。单个快速时钟会重复，但慢速时钟和其他时钟仍提供
额外区分信息。

可以把每个位置的编码看成一组时钟读数：

```text
位置 p → [时钟1读数, 时钟2读数, ..., 时钟64读数]
```

不是看某一只时钟，而是看整组读数。于是：

```text
单个维度：可能重复
多个不同频率一起看：在有限上下文范围内通常能区分
```

这也解释了 RoPE 的限制：

- 它不是数学上对无限位置都唯一的编码，足够远时仍可能发生周期碰撞。
- 长上下文外推需要额外设计，例如调整 RoPE 频率或使用位置缩放。
- `rope_base`、head_dim 和上下文长度会影响这些周期，不同模型不能直接照搬数值。

再回到 Q/K：位置 2 和位置 5 的某一对特征可能已经绕了一圈，但其他频率没有；
Q/K 点积综合所有维度，因此仍能携带相对位置差异。

**记忆句：不是一只指针记位置，而是一组转速不同的指针共同组成位置密码。**

## 3. gate/up/down：一条产生特征，一条调节特征，最后组合输出

仍然看某个位置的一行 1024 个数。可以把 FFN 想成一台具有很多通道的调节台：

```text
同一行输入 x：1024个数
    |
    |---- up_proj ----> 3072个待加工特征 ------------------|
    |                                                    |
    |---- gate_proj --> 3072个数 --> SiLU --> 3072个系数 ---|→ 逐通道相乘
                                                           |
                                                           v
                                                       3072个数
                                                           |
                                                       down_proj
                                                           |
                                                           v
                                                       1024个数
```

“特征”和“系数”是解释两条分支在乘法中的作用，不是固定语义标签。
两条分支都从同一个 x 计算，但权重不同，不是把 x 复制成同样的两份。
这些数也不一定对应“颜色”“语法”等可单独命名的属性。

| 名称 | 可以怎样记 | 实际动作 |
| --- | --- | --- |
| `up_proj` | 展开待加工特征 | 学习到的线性投影，`1024 → 3072` |
| `gate_proj` | 产生输入相关的调节信号 | 另一套独立的线性投影，`1024 → 3072` |
| `SiLU` | 平滑变换调节信号 | 对每个数应用 `z*sigmoid(z)`，形状不变 |
| 逐元素乘法 | 每个通道乘自己的系数 | 第 i 个系数乘第 i 个特征，不是求和，也不是 Attention |
| `down_proj` | 把中间结果重新组合为主路径格式 | 学习到的线性投影，`3072 → 1024` |

up/down 描述这里的特征维度变化，不是增加/减少 token 数或移动层的位置。
down 不是简单丢掉后面 2048 个数，而是对全部中间通道进行学习到的线性组合。

### 更形象的理解：一个调音台

先不要把它想成三层数学公式。把某个位置的向量 `x` 想成一张订单，
FFN 里面有一台包含 3072 个通道的调音台。

```text
                         ┌── up_proj ───→ 产生声音
x ───────────────────────┤
                         └── gate_proj ─→ 产生音量旋钮
                                      ↓
                                    SiLU
                                      ↓
                              调节每条声音
```

这两条线路**同时接收同一个 x**，不是前后串联。

假设为了演示只保留 3 个中间通道：

```text
up_proj(x)   = [10, 10, 10]   # 三条待加工的声音
gate_proj(x) = [-2,  0,  2]   # 三个调节信号
```

gate 信号经过 SiLU：

```text
SiLU(-2) ≈ -0.238
SiLU(0)  =  0
SiLU(2)  ≈  1.762
```

再逐通道相乘：

```text
声音：[10, 10, 10]
旋钮：[ -0.238, 0, 1.762]
结果：[-2.38, 0, 17.62]
```

于是：

```text
通道 A：被反向影响
通道 B：被关闭
通道 C：被放大
```

这里的“声音”“旋钮”只是帮助理解，不代表某个真实通道就叫“物体”“动作”
或“温度”。实际通道是学习出来的数值组合。

然后 `down_proj` 像混音器，把 3072 条中间通道重新混合成 1024 个数：

```text
3072 条中间通道
        ↓ down_proj：学习如何混合所有通道
1024 个主路径特征
        ↓
原来的 x + FFN 输出
```

它不是简单删除后面 2048 个通道，而是类似：

```text
输出1 = 通道1×权重 + 通道2×权重 + 通道3×权重 + ...
输出2 = ...
```

所以整个过程可以记成：

```text
up_proj：产生候选特征
gate_proj：产生每个特征的调节信号
SiLU：把调节信号变得平滑
逐元素相乘：逐通道控制强弱
down_proj：重新混合，回到主路径维度
```

一句话：

> 一条线路制造内容，一条线路控制音量，最后把所有通道混音输出。

## 4. SiLU：平滑调节，但不是概率开关

公式：

```text
sigmoid(z) = 1 / (1 + exp(-z))
SiLU(z) = z * sigmoid(z)
```

容易混淆的是：`sigmoid(z)` 在 0 到 1 之间，但再乘 z 后的 `SiLU(z)` 不受
这个范围限制。正的大数接近原值；非常负的数接近 0 的负侧；中等负数仍然为负。

用三个通道看整个门控乘法，数值都是人为示例：

| 通道 | up 分支特征 u | gate 原始值 g | `SiLU(g)` | 最终 `u*SiLU(g)` |
| --- | --- | --- | --- | --- |
| A | 10 | -2 | -0.2384 | -2.3841 |
| B | 10 | 0 | 0 | 0 |
| C | 10 | 2 | 1.7616 | 17.6159 |

同样的待加工特征 10，在不同系数下可以被压低、变成 0、放大或改变符号。
所以“阀门”“调节旋钮”只是一种类比：它不是只能开关两档，也不是只能减弱信号。
这不是 MoE 的 Top-k 专家路由，不是在选择要调用哪个专家。

SiLU 的“激活”不是人工判断 token 是否重要，而是确定的逐元素数学函数。
它和门控乘法一起提供非线性变换。若仅将多个线性层串联，仍然可以合成一个
线性层；但不能反过来说“去掉 SiLU 后整个 SwiGLU 就线性了”，因为两分支
相乘本身也有非线性。

## 5. 对照本仓库的名字

模型权重文件里的名称，与教学代码的对应关系：

| 权重名称 | 仓库成员 |
| --- | --- |
| `gate_proj` | `FeedForward.fc1` |
| `up_proj` | `FeedForward.fc2` |
| `down_proj` | `FeedForward.fc3` |

参考 [FeedForward.forward](../reasoning_from_scratch/qwen3.py)：

```python
g = self.fc1(x)
u = self.fc2(x)
h = torch.nn.functional.silu(g) * u
output = self.fc3(h)
```

公式记成：

```text
FFN(x) = down_proj(SiLU(gate_proj(x)) * up_proj(x))
```

所有位置分别执行相同的 FFN。一个位置的 FFN 不去读取其他位置，
但其输入已经可能包含前面 Attention 汇集的上下文。
输出回到 1024 维后，Block 的外层代码再做残差相加；相加不是 `down_proj`
自己完成的。
